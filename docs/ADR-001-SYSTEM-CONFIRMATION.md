# ADR 001: безопасный handle системного подтверждения

Дата: **20 октября 2026**. Статус: **решение принято и реализовано; результаты 1.2.2 приведены в VERIFICATION**.

## Проблема

Package Installer возвращает Intent подтверждения, который может содержать Binder и токены защиты запуска. На эмуляторе Google APIs API 37 попытка сохранить его через `Parcel.marshall()` завершилась `RuntimeException: Tried to marshall a Parcel that contains objects (binders or FDs).` Ошибка воспроизведена в диагностическом запуске; локальный лог — `.toolchain/qa122/api37/confirmation-diagnostic-error.txt`.

Parcel предназначен для IPC. Android прямо исключает его marshalled-представление из поддерживаемых форматов долговременного хранения: формат может меняться между версиями платформы. См. [Parcel.marshall()](https://developer.android.com/reference/android/os/Parcel#marshall()). Поэтому даже отсутствие Binder в отдельном тестовом Intent не делает его Parcel-байты допустимым форматом журнала.

Нужно сохранить исходное системное подтверждение, корреляцию с сессией и возможность обработки позднего результата. Восстановление не должно повторно выполнять commit, терять подготовленные файлы или снимать защиту запуска Android.

## Решение

Для исходного Intent создаётся **immutable activity PendingIntent**, которым владеет Android. Исходные extras, Binder и токены защиты остаются в системном объекте. Приложение не переносит их в JSON, Base64, Parcel-байты или реконструированный Intent. Android описывает PendingIntent как ссылку на системный токен и определяет его идентичность через фильтруемые поля Intent, request code и flags; extras не создают отдельной идентичности. См. [PendingIntent](https://developer.android.com/reference/android/app/PendingIntent).

В журнал записывается только ограниченный **envelope v1**:

| Поле | Назначение |
| --- | --- |
| Версия `1` | Явный формат и проверка совместимости |
| `sessionId` | Сессия Package Installer |
| UUID поколения | Различает подтверждения, в том числе после замены операции |
| `requestCode` | Часть идентичности PendingIntent |
| URI фильтра Intent | Поля для поиска того же PendingIntent; без extras |

Процесс хранит PendingIntent в ограниченном реестре с сильными ссылками. Это удерживает handle во время жизни процесса, включая переход receiver → UI. После пересоздания процесса выполняется только поиск существующего handle через `FLAG_NO_CREATE` с той же идентичностью и `FLAG_IMMUTABLE`. Из envelope новый подтверждающий Intent не создаётся. Доступность системного токена после гибели процесса не гарантируется: холодное восстановление — best effort.

До UI-события envelope должен быть сохранён с подтверждённым `flush()`. UI проверяет session/generation непосредственно перед попыткой запуска и запускает sender при lifecycle не ниже `STARTED`. Передаются sender-side `ActivityOptions`: `MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE` на API 36+, `MODE_BACKGROUND_ACTIVITY_START_ALLOWED` на API 34/35 с тем же ограничением lifecycle. ACK означает попытку запуска; итог установки приходит отдельно. Мутация ACK условна по текущим session, generation и состоянию подтверждения: событие, проверенное до приостановки, не может перезаписать более новое состояние журнала. Основание — [правила безопасного запуска Activity](https://developer.android.com/guide/components/activities/secure-bal). `removeLaunchSecurityProtection()` не вызывается.

Сначала окончательный результат установки записывается и подтверждается на диске. Только затем отменяется obsolete PendingIntent соответствующего поколения. Ошибка durable-записи не разрешает преждевременно отменить handle; чужая сессия или новое поколение не затрагиваются.

## Неопределённый результат и миграция

Отсутствующий, отменённый или недопустимый handle, а также legacy-запись с сериализованным Intent переводят восстановление в **UNKNOWN**. Старые Parcel-данные не декодируются как запасной путь. Рабочий каталог, выбранные APK и корреляция сессии сохраняются; поздний подтверждённый callback может завершить соответствующую операцию. UNKNOWN не запускает commit, не отменяет запечатанную Android-сессию и не удаляет файлы, нужные для выяснения результата.

## Альтернативы и компромиссы

- Сохранять Parcel-байты: непригодно по контракту Android и воспроизведённому отказу с Binder.
- Удалить extras, реконструировать Intent или снять защиту запуска: теряются непрозрачные данные и гарантии системного подтверждения.
- Хранить только Intent в памяти: пересоздание процесса полностью теряет handle; в выбранном варианте остаётся возможность найти системный токен.
- Гарантировать восстановление после гибели процесса: такой гарантии выбранный API не даёт. Цена решения — явный UNKNOWN при недоступном токене вместо неподтверждённого действия.

## Проверка

Нужны тесты envelope v1 и его ограничений, отсутствия extras/Parcel, session/generation correlation, stale callbacks, найденного и отсутствующего `NO_CREATE`, legacy-записей, ограниченного реестра и порядка durable finish → cancel. Ошибка записи результата должна сохранять возможность поздней обработки.

На выделенных API 34 и API 37 проверяются реальные Binder-bearing подтверждения, обычная установка, обновление отключённого приложения, пересоздание Activity, потеря процесса, отменённый токен и запоздалый результат. Запуск в фоне не должен обходить lifecycle/BAL. Для каждого исхода фиксируются точный APK, fingerprint, способ завершения процесса, журнал и фактическое состояние Package Manager. Один успешный cold restore не означает гарантированное восстановление на всех устройствах. Завершённые результаты помещаются в [VERIFICATION](VERIFICATION.md).
